# 代码审查

对当前工作区的改动进行全面审查。先运行 `git diff` 查看所有未提交的改动，然后逐项检查。

## 审查清单

### 1. 正确性
- [ ] 逻辑是否正确？有没有 off-by-one、空指针、类型混淆？
- [ ] 错误处理是否完整？异常是否被吞掉？错误信息是否对用户有帮助？
- [ ] 边界条件是否处理？空输入、null、超大输入、负数、Unicode？
- [ ] 并发安全？有没有竞态条件、死锁风险？
- [ ] 资源是否释放？文件句柄、数据库连接、锁、内存？

### 2. 安全性
- [ ] 有没有硬编码的密钥、token、密码、内网 URL？
- [ ] 用户输入是否经过验证和清理？有没有 SQL 注入、XSS、路径穿越风险？
- [ ] 权限检查是否到位？用户能否访问不该访问的数据？
- [ ] 有没有使用不安全的加密/哈希/随机数？
- [ ] 敏感信息是否出现在日志或错误信息中？

### 3. 性能
- [ ] 有没有 N+1 查询？循环内重复的 I/O？
- [ ] 数据结构选择是否合理？有没有 O(n²) 可以 O(n) 的？
- [ ] 大数据集是否分页/流式处理？会不会 OOM？
- [ ] 有没有不必要的同步阻塞？可以用异步的地方？
- [ ] 缓存是否合理？有没有缓存失效/一致性问题？

### 4. 可维护性
- [ ] 命名是否清晰？函数/变量名是否表达了意图？
- [ ] 函数是否太长（>50 行）？职责是否单一？
- [ ] 嵌套是否太深（>3 层）？能否用提前 return 简化？
- [ ] 有没有魔法数字/字符串？应该提取为常量？
- [ ] 注释是否解释了"为什么"而不是"做什么"？
- [ ] 是否符合项目的代码风格和约定？

### 5. 测试覆盖
- [ ] 新功能是否有对应测试？
- [ ] 边界条件和错误路径是否被测试覆盖？
- [ ] 测试是否有意义？不是单纯凑覆盖率？
- [ ] 测试是否因为这次改动而需要更新？
- [ ] 有没有引入难以测试的设计（硬编码依赖、全局状态）？

## 输出格式

按严重程度分类报告问题：
- **严重**：必须修复（安全漏洞、数据丢失风险、崩溃）
- **警告**：建议修复（性能问题、可维护性差、测试缺失）
- **建议**：可选改进（命名、风格、小优化）

每个问题给出：文件:行号、问题描述、建议修复方式。
