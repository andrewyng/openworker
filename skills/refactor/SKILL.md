# 安全重构

重构的前提是：**不改变外部行为，只改善内部结构**。

## 前提条件
1. **必须有测试**：重构前确认已有足够测试覆盖。如果没有，先用 `/test-gen` 生成测试。
2. **测试必须通过**：运行现有测试，确认全部绿色后再开始。
3. **小步迭代**：每次只做一个小重构，运行测试，再下一步。不要一次性大改。

## 重构手法

### 提取（Extract）
- **提取函数**：一个函数超过 20 行或有多个抽象层级 -> 拆分
- **提取变量**：复杂表达式 -> 用有意义的变量名拆分
- **提取类/模块**：一个类承担太多职责 -> 按职责拆分
- **提取常量**：魔法数字/字符串 -> 命名常量

### 内联（Inline）
- **内联函数**：函数体比函数名还清晰 -> 删除函数，直接用代码
- **内联变量**：变量只用一次且不增加可读性 -> 直接用值
- 过度抽象比不够抽象更糟糕

### 简化（Simplify）
- **用早返回替代嵌套**：`if (!valid) return` 替代深层 if-else 嵌套
- **用多态替代 switch**：类型判断散落各处 -> 策略模式/方法重写
- **用映射替代长 if-else**：`MAP[action]()` 替代 `if action == 'x' ... elif ...`
- **合并重复代码**：相同逻辑出现 3 次以上 -> 提取公共函数

### 移动（Move）
- **移动函数**：函数用的数据在另一个类 -> 把函数移过去
- **移动字段**：字段被另一个类频繁使用 -> 考虑迁移
- **移动语句**：相关代码分散 -> 集中到一起

## 安全检查
- 每步重构后运行测试
- 如果重构后测试失败，立即回退（git checkout），分析原因
- 不要在重构中"顺手"修 bug 或加功能--那会让重构难以审查
- 不要在重构中改公开 API（函数签名、返回值结构、异常类型）
- 注意：重构不改变可观察的行为，包括性能特征

## 重构信号
当你看到以下情况，考虑重构：
- **重复代码**：复制粘贴的代码块
- **过长函数**：超过 50 行的函数
- **过大类**：字段/方法超过 20 个的类
- **过长参数列表**：超过 4 个参数
- **发散修改**：一个类因不同原因被修改
- **霰弹修改**：一个改动需要修改多个类
- **特性依恋**：方法用了另一个类的数据比自己类的还多
- **数据泥团**：相同几个字段总是一起出现
