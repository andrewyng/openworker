## Tooling note (read before trusting the numbers)

- **No MCP tools this run.** Only `github` + `filesystem` MCP servers are wired to this
  persona's MCP list, so `mcp__arxiv__*` and `mcp__qdrant__*` were unavailable. The task's
  "follow this order" tool-call instructions could not be honored literally. I fell back to the
  documented API surface instead, which is exactly what the existing helper scripts in this folder
  already use:
  - arXiv searches and abstract reads → **arXiv Atom API** via `curl -L`
    (`https://export.arxiv.org/api/query`, `cat:` category + `abs:` full-text filters,
    `sortBy=submittedDate,descending`).
  - Dedup check → **Qdrant `POST /points/scroll`** over `localhost:6333`.
  - Store → **Qdrant `PUT /collections/default/points`** with `{"points":[...]}` body,
    384-dim MiniLM embeddings via fastembed under vector name `fast-all-minilm-l6-v2`.
- **arXiv was flaky:** `export.arxiv.org` intermittently returns a 404 HTML error page
  (rate-limit / cache flap) under load. Every call was wrapped in exponential-backoff retry.
- **Qdrant search endpoint quirk persists** (known from 2026-08-20/28 runs): the
  `/points/search` shape on this build keeps returning
  `Wrong input: Not existing vector name` / `Format error: missing field vector` for every request
  shape tried. This is a retrieval-side limitation of the running Qdrant, **not** a defect in what
  was stored — points, their payload, and 384-dim vectors are present (confirmed via
  `with_vector=True` scroll). `indexed_vectors_count` is 0, so HNSW indexing is still lazy;
  retrieval verification was therefore done via **scroll**, which is authoritative for "is it
  stored." Anyone doing vector search should retry the request shape or let indexing run.
