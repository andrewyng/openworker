## 1. ROCm — 7.1.0 is stale; 7.14.0 is current and it's a structural shift
**Likelihood: HIGH — most things below depend on it.**
- Latest ROCm core SDK is **7.14.0, released 2026-07-16**; 7.2.4 also exists in the series. You are 13 minor versions behind at 7.1.0.
  - https://github.com/ROCm/ROCm/releases (opened; release 7.14.0, tag rocm-7.14.0, commit 830cc1b, "released this, 16 Jul 03:28")
- **7.14.0 transitions ROCm to TheRock**, a modular build/release system: leaner core SDK, optional domain SDKs (AI/HPC), separately versioned pip wheels. This is a real breaking change for any flow that assumes the old monolithic layout, and it changes the gfx1151 nightly index URLs you install torch from.
  - Same URL as above ("ROCm Core SDK 7.14.0 transitions ROCm to TheRock … modular architecture … transition guide")
- 7.14.0 explicitly adds **Ryzen AI MAX+ PRO 495/490/485 (gfx1151)** to the supported APU list, plus 7.13-series APUs — positive news for Strix Halo, but it moves the supported target forward of your 7.1.0.
  - Same URL as above ("ROCm 7.14.0 adds support for … AMD Ryzen AI MAX+ PRO 495 (gfx1151)…")
- The segfault class you hit with ROCm 7.1 on Strix Halo (torch._grouped_mm / VRAM access crashes) is a known issue cluster, e.g. https://github.com/ROCm/ROCm/issues/5853 and https://github.com/pytorch/pytorch/issues/173367 (both surfaced in search results; not individually opened). The forward-fix path is a newer ROCm from TheRock, which is exactly the 7.14 direction — treat 7.1.0 as unsupported-buggy for gfx1151.

## 2. torch 2.11.0+rocm7.13.0 (gfx1151 nightly index) — nightly drift + silent CUDA substitution risk
**Likelihood: HIGH (silent breakage is the failure mode).**
- The gfx1151 nightly index is live and rolling: users report wheels like `torch 2.11.0a0+rocm7.11.0a20260106` and `rocm 7.11.0a20260111` at `https://rocm.nightlies.amd.com/v2/gfx1151/` (opened: https://github.com/ROCm/TheRock/issues/2849 — closed, Strix Halo gfx1151 on Arch). A nightly newer than your 7.13.0 build has therefore certainly shipped; I did not open the nightly index itself, so I'm not naming a "current" version.
- Same issue #2849 documented a **pip dependency-loop when force-upgrading `rocm[libraries,devel] torch torchaudio torchvision` together on gfx1151** (50 GB of downloads, no convergence) — a known pain point if you do `pip install -U` carelessly.
- **Silent CUDA substitution**: documented in practice — after `pip install -U unsloth`, PyPI's CUDA torch can replace the ROCm build, and you must re-install from the gfx1151 index.
  - https://sleepingrobots.com/dreams/unsloth-studio-strix-halo/ (search result: "Running pip install -U unsloth can pull CUDA PyTorch from PyPI, silently replacing the ROCm build")
  - https://www.amd.com/en/developer/resources/technical-articles/2026/train-and-run-models-on-amd-gpus-with-unsloth.html (official AMD/Unsloth article, 2026-07-20 — snippet level only, not opened in full)
- Action: after any pip upgrade of unsloth/adjacent deps, run `torch --version` and check `torch.version.hip`; re-pull from the gfx1151 nightly index if it reads cuda.

## 3. transformers — you're 10 minors behind (5.5.0 → 5.15.1); your known break class is already in-tree
**Likelihood: MEDIUM-HIGH for the `trust_remote_code` break you flagged; patch upgrades from 5.5.0 are lower risk.**
- Latest is **v5.15.1, released 2026-08-19** (yesterday). You're on 5.5.0 (released ~April 2026).
  - https://github.com/huggingface/transformers/releases (opened; v5.15.1, commit 550d7b3, "released this, 19 Aug 10:50"; patch fix DFlash/MTP/Lanczos, no breaking claims)
- The trust_remote_code break class you asked about is real and documented against exactly v5.x:
  - `is_torch_fx_available` removed in 5.0 breaks Hub models using trust_remote_code — https://github.com/huggingface/transformers/issues/44561 (opened; confirmed removal via #37234)
  - Concrete repro on transformers 5.3.0 with moonshotai/Kimi-K2.5 (import error on the removed symbol) — https://github.com/huggingface/transformers/issues/45020 (opened; closed)
  - 5.5.0 itself: "Remote code execution support has been removed from the native LightGlue integration … remove trust_remote_code=True" — https://github.com/huggingface/transformers/releases/tag/v5.5.0 (via search)
- Implication: any Hub model whose bundled code imported v4-era `transformers.utils` symbols will fail on your 5.5.0 **and** on 5.15.1; upgrading transformers won't fix those, pinning the model revision to an older revision or updating the model repo will. No breaking-change advisory was found for the 5.5.0→5.15.1 patch path itself; patch notes I read are bug-fix scoped.
- No CVE found in what I opened.
