## 1. HIGH — ROCR runtime busy-spin bug, affects the exact torch wheel you run (OPEN, filed Aug 1)

New gfx1151 bug: the ROCR runtime bundled in TheRock **nightly AND 7.14
production wheels** leaves `AsyncEventsLoop` spinning 100% of one CPU core
permanently after any GPU op. The reporter says "release-channel ROCR 1.18
clean on same kernel" but nightly/7.14 not. Your installed
`torch==2.11.0+rocm7.13.0` sits in that affected wheel family.
Symptom to look for: one core pegged at 100% after any `torch.cuda`/ROCm op.

- https://github.com/ROCm/TheRock/issues/7051 (opened 2026-08-01, status: triage)

## 2. MEDIUM-HIGH — Newer ROCm exists (7.13/7.14); the 7.1 `torch._grouped_mm` segfault appears resolved in 7.13

- ROCm **7.14 production wheels** now exist (referenced in TheRock #7051 above).
- Unsloth merged/verified fix for Strix Halo: `_check_torch_grouped_mm_supported()
  == True, no segfault` on `gfx1151 / Radeon 8060S` with ROCm 7.13 nightly, and
  `pip download` still resolves `torch==2.11.0+rocm7.13.0` from the AMD index —
  i.e. the 7.1 grouped_mm segfault that bit you is gone in the build you run.
  Also: AMD now ships **native gfx1151 kernels** in TheRock nightly, so
  `HSA_OVERRIDE_GFX_VERSION` is no longer needed.
  - https://github.com/unslothai/unsloth/pull/5301
  - https://github.com/ROCm/ROCm/issues/6034 (March 2026, 5 bf16 bugs found on gfx1151 — older, context only)

Do **not** downgrade to ROCm 7.1 wheels if you see CUDA-flavoured or
inconsistent resolution — the gfx1151 index is still the right source
(https://rocm.nightlies.amd.com/v2/gfx1151/ — fetched today, still serves
dedicated `+rocm` wheels, no CUDA substitution observed).

## 3. MEDIUM — transformers 5.5.0 → 5.15.0 shipped (Aug 10), with real breaking changes

Latest release is **v5.15.0** (2026-08-10). You're on 5.5.0. Documented
breaking changes if you upgrade:
- Linear-attention models (Mamba, GDN): **kernels are now opt-in**, not
  auto-selected. If you relied on auto kernel selection, behaviour silently changes.
- Cache-cropping API now **rejects positive (absolute) sizes**, negative only.
- T5 family: SDPA enabled by default; eager-only assumptions break.
- Private processor helpers (`_is_url`, `_build_image_tokens`) removed.

- https://github.com/huggingface/transformers/releases/tag/v5.15.0

No `trust_remote_code`-specific breaking note found in the v5.15.0 notes
(opened and read the page; not mentioned). My one targeted search for
"transformers trust_remote_code removed" returned zero results — treat this
area as unchanged, not confirmed-safe.
