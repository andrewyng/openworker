### 1. TOP RISK (MOVED — net-new activity) — gfx1151 AsyncEventsLoop 100%-CPU-spin, now a **second spin class**
**ON-FOCUS (workstation-stack / the training path — FOCUS item 4). Likelihood: HIGH (top gfx1151 runtime risk); status: MOVED this run — first real progress note on the issue since 08-13, no fix yet.**

- **TheRock #7051 — CHANGED.** state=**open**, `status: triage`, assignee **adityas-amd**, **5 comments** (was 4), created 2026-08-01, last updated **2026-09-01T22:28:04Z** (was **2026-08-13** in 09-01). The 5th comment is by **leapdragon**, dated 2026-09-01T22:27:40Z, opened in full this run.
  - https://api.github.com/repos/ROCm/TheRock/issues/7051
  - **What leapdragon added (verbatim-sourced, from the comment this run):**
    1. **A second affected GPU:** the bug now reproduces on **Navi 21 (gfx1030)** — 4× Radeon PRO V620, ROCR **1.21.0** from the `therock-7.14.1` gfx103X tarball (rocm-systems @ `ca887ee`), serving vLLM TP=4. Every HIP process pinned a core at idle; the 5-process stack idled at ~9 cores. So this is no longer gfx1151-only.
    2. **A second, distinct spin class:** class 1 is `Runtime::AsyncEventsLoop` polling mode (this issue — any registered async signal without an EopEvent flips the loop into polling with no backoff, one spinner per process). **Class 2 is `InterruptSignal::WaitRelaxed` livelock on the HIP service thread**, which "appears once RCCL is initialized" — **one spinner per TP rank**, reproducer `init_process_group("nccl")` + one `all_reduce` + sleep. leapdragon links class 2 to "the same family as ROCm/ROCm#6522's post-eviction livelock."
    3. **Workarounds measured *ineffective* for the multi-GPU / RCCL case:** `HSA_ENABLE_INTERRUPT=1`, `ROC_ACTIVE_WAIT_TIMEOUT=0`, `HSA_ENABLE_MWAITX=1`, and `hipSetDeviceFlags(hipDeviceScheduleBlockingSync)` (silences single-GPU class-1 but not a ≥2-device process, where an event-less signal exists regardless).
    4. **A concrete patch:** adds a bounded backoff at the four spin sites (AsyncEventsLoop polling; `BusyWaitSignal::WaitRelaxed`; the forced-ACTIVE branch of `Signal::WaitMultiple`; and one more). **Under AMD's hands — not merged, triage still open.**
    5. **Severity reframed (AU-specific):** on the APU silicon these wheels target, the spin **costs double-digit render time** (~14% on a sibling's LTX-2.5 run, Tctl 98→51 °C), not just a parked core. That's the datapoint leapdragon frames as the reason it should leave triage.
  - **Why this moves it (and why it does not "fix" it):** there is still no merged fix and it is still `status: triage`. But the issue just got materially richer — a second GPU family, a second spin class, an RCCL/multi-GPU angle (relevant if the box ever does tensor-parallel work), and a patch awaiting the assignee. The 09-01 "zero movement" line is now closed; activity resumed 2026-09-01.
  - **Relevance to THIS box — a refinement, not a downgrade.** My 09-01 write-up framed #7051 as living on the *7.14* line, "a different RROCr version than your 7.1.0/7.13.0." That understated it. #7051's **own reproduced matrix** lists `rocm==7.13.0a20260411 nightly + torch 2.12.0a0+rocm7.13.0a20260411` as **bundling ROCR 1.21 and spinning** — i.e. the **7.13.0 nightly wheel line is within the affected range**. Your host runs **torch 2.11.0+rocm7.13.0 from the gfx1151 nightly index**, which is that same 7.13.0-nightly family. **So if your nightly wheel is the 1.21-bundled one, the spin is on your box, not merely a future line.** The clean arm is the release-channel 7.1.0 runtime (ROCR 1.18), which #7051 measured at 0% idle spin on the same kernel. **Recommended 30-second check** (not done by me, no box access): run `strings` on your bundled `libhsa-runtime64.so` and read off its ROCR build ID — `1.21.*` means you're on the affected wheel and the 1.18 preload shim from below is the mitigation; `1.18` means you're on the clean release-channel runtime. (This is inference from the issue's matrix + your wheel line; I did not open your box's `/proc/PID/maps`.)
  - **Mitigation (carried, still the only known stopgap):** the `LD_PRELOAD`-a-1.18-runtime shim from isaac-ranger's earlier comments (#5225839911, #5228549887) — uninvites the 1.21 runtime, 0-tick idle, byte-identical output. leapdragon's note carries an important caveat: **the required stub count is not stable** — the 1.21-vs-1.18 `nm -D` diff is **19** symbols on one stack, **15** on another, **10** on a third (different `1.18.702xx` patchlevel), so **regenerate the stub list from your own two runtimes, don't copy anyone's "fifteen."** A downstream ComfyUI image (`baramofme/comfyui-rocm-triton-flashattn`) now bakes the 1.18 preload citing this issue.
