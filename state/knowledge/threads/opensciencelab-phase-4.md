## History
- 2026-08-26 — Phase 4 Step 2 (materials) is BLOCKED by a verify-image install defect, NOT an adapter bug. Two distinct facts: (1) The PyPI package `chgnet==0.4.2` pinned in the Dockerfile is a SQUATTED package — different API generation from CederGroupHub/chgnet. It exposes neither `StructureRelaxer` nor `get_eform_energy` nor `get_forces` (the three symbols the opensciencelab adapter calls). Only `CHGNet.predict_structure` exists, under `chgnet.model.model`. Its PyPI requires_dist = ase/cython/pymatgen/torch/wandb (not the real chgnet's dep set). (2) The `pymatgen==2024.9.10` package IS fully installed (282 .py files, full subpackage tree incl. core/) but its top-level `__init__.py` is MISSING (pymatgen/__path__ exists, no pymatgen/__init__.py listed in RECORD), so `from pymatgen import Lattice, Structure` fails with ImportError and the adapter's `_HAVE_PYMATGEN` = False. `from pymatgen.core import Lattice` works fine. NET EFFECT: In the verify image, `ChgNetAdapter.available()` is always False. live_verify.py reports G2 Vina GREEN, G4 PySCF GREEN, G3 CHGNet RED ("not importable", 5 GREEN / 2 RED). The 102 host tests still pass (they fake-kernel the chgnet module), but the CHGNet kernel has NECESSARILY never produced a real E_form number in this image. Phase 4's "one real materials Pareto front" requirement cannot be met until chgnet is switched to a package that actually exposes the three adapter symbols. FIX OPTIONS (each a root-level change, needs user sign-off): A. Change the Dockerfile pin to a working chgnet source: e.g. `pip install "chgnet @ git+https://github.com/CederGroupHub/chgnet@main"` (git not in image — need to add `git` to base apt-get, or use a wheel build); or pin a version whose API matches. B. If the real chgnet (GitHub main) is what the adapter targets, the Dockerfile's PyPI chgnet 0.4.2 is the wrong package entirely — needs replacement. ROOT CAUSE CLARITY: The bug is in the Dockerfile pin + pymatgen wheel packaging, not in opensciencelab/chgnet.py, materials.py, or base.py.
