## 1. ALTERNATIVE APPROACHES (not the one in use)

**Alternative A — Treat the harness as a service; build only your contract on top of a provider harness API.**
The Aug-2026 "Harness Engineering" literature is explicit that the default path is no longer "build your own loop," but "pick a harness framework, configure the four pillars (system prompt, tools, context, subagents), and spend your effort on domain-specific prompt + tool design" (augmentcode, "Harness Engineering for AI Coding Agents," read). Claude Agent SDK, Codex SDK, OpenAI Agents SDK "all point in the same direction… you get the loop, the tools, the context management, the hooks, and the sandbox primitives out of the box" (onemancrew.dev, "The Death of Frameworks, The Rise of the Harness," read). The killer data point: "On Terminal Bench 2.0, Claude Opus 4.6 running inside Claude Code scores far lower than the same model running in a custom harness. Viv's team moved a coding agent from Top 30 to Top 5 by changing **only the harness**" (addyosmani.com/blog/agent-harness-engineering, read). *What it buys:* you stop building the commoditized chassis (sandbox, context compaction, retry loop) and redirect the ~5 build steps into the only thing that's hard and defensible — your contract/spec-drift layer. *What it costs:* you hand the "verifiable runtime" guarantee to a provider you don't control, which is exactly the trust property you're trying to sell; and the same Agent-Reactive-Bugs problem (§3) means their harness reacts to your LLM in ways you can't patch.

**Alternative B — Design-by-contract as an orthogonal add-on, not baked into every layer.**
AgentAssert (Varun Pratap, "Design-by-Contract for AI Agents," `pip install agentassert-abc[yaml,math]`) and the AgentContract-Bench/ABC line (arXiv:2602.22302, "Agent Behavioral Contracts: Formal Specification and Runtime Enforcement") both define hard/soft invariants, runtime drift detection, and a reliability composite — as a **separate layer** interposed on the loop. agpack's Conformance **Tier B** ("live-spec fetch + draft-drift") is the same idea, discovered independently. *What it buys:* drift detection as a reusable, testable component you don't have to re-derive as a Step; the "verifiability" surface (a contract an external verifier can check) stays decoupled from your sandbox/audit internals. *What it costs:* another boundary, and a tool that itself has not been stress-tested against adversarial agents (AgentAssert's own page reports a single Θ=0.9541 reliability score — it's a product claim, not a replicated benchmark).

**Alternative C — "Blueprint first, model second": codify the workflow deterministically, restrict the LLM to a tool role.**
Source Code Agent / "Blueprint First" (arXiv:2508.02721, read) codifies operational logic into deterministic source-code blueprints and constrains the LLM to act as a specialized tool within a predictable workflow; on τ-bench it beat the strongest baseline by 10.1 points "and drastically enhanced execution efficiency" while being deterministic. This is the mirror image of agpack: rather than wrapping an agentic loop in a trust cage, make the loop itself deterministic and let the LLM only decide within it. *What it buys:* verifiability by construction (the execution path is inspectable code, not an agent's trajectory) — a far cheaper "verifiable" guarantee than any proof-of-identical-execution. *What it costs:* it gives up exactly the agent freedom that made the problem interesting in the first place; it is a different bet about where the value lives (planning vs. execution).

## 2. PRIOR ART (who already built this?)

- **AgentContract-Bench / ABC** (arXiv:2602.22302, "Agent Behavioral Contracts" — read in full) is the *direct* prior art for the conformance/spec-drift half of agpack. It is "to our knowledge, the first benchmark specifically designed for behavioral contract enforcement in autonomous AI agents," combining trace evaluation, formal compliance metrics grounded in an ABC framework, adversarial stress testing, and explicit "**Drift Prevention via Contracts**." It also provides a contract-spec language (ContractSpec) with hard invariants (no PII leakage, mandatory disclaimers) and soft invariants — exactly the hard/soft split agpack is building by hand. *If you are reinventing Conformance Tier B, don't.*
- **AgentAssert** (varunpratap.com/products/agentassert, read) — the same idea as a drop-in: hard vs. soft constraints (hard halt execution, soft degrade-and-log), "Real-Time Drift Detection… semantic drift before it compounds into a catastrophic failure downstream," and a composite reliability score Θ. *If your conformance surface is the product, this exists.*
- **HARNESSFIX** (arXiv:2606.06324, "From Failed Trajectories to Reliable LLM Agents," read) is the prior art for *why you need the trust layer at all*, and for why your from-scratch build will have the bugs it has: it introduces HTIR (Harness-aware Trace IR) to bridge "runtime failures and static code implementation," pinpointing which of trace/data-control/implementation-anchor layers failed. It treats harness flaws as a first-class cause of failure, not "bad model output."
- **Progent** (cited in AgentVerify, preprints.org/202604.1029) — "the first privilege control framework for LLM agents," interposing on tool calls with a boolean-predicate DSL, fallbacks (terminate/inspect/feedback), "deterministic, provable security guarantees with negligible overhead." agpack's `metered.py` / `Scope` policy gate is the same move, re-derived.
- **The "death of frameworks, rise of the harness" + Harness-as-a-Service** line (augmentcode; onemancrew.dev) is the *market* prior art: the verdict is that the bespoke harness is becoming the commoditized chassis and the moat is moving *out* of it. That's an argument about where your effort is worth, which is the argument of §3.

## 3. THE CASE AGAINST (explicit criticism)

**1. The linchpin claim is already self-discredited, and the literature says cross-engine verifiability is fragile.** Your own 2026-08-30 caveat admits the portability proof "is NOT a true cross-engine test," because both drivers share the same pure-Python exec path and DeterministicFingerprintDriver "only re-wraps output." So `run_portability_proof` verifies *the contract* (same bundle bytes → same computed value) but **does not test real cross-engine behavior**. And arXiv:2509.11068, "Tractable Asymmetric Verification" (read in full), empirically nails the fragility: deterministic LLM replicability holds on one GPU (RTX 4000 Ada) and *fails* on another (A40) "from minute, non-malicious floating-point discrepancies." The paper's own conclusion: "a standardised execution environment… is a prerequisite," and cross-hardware verification breaks unless you accept it. **Your portability proof asserts determinism across engines you have never actually varied — the claim it's most being used to support is unproven, and known to be hardware-fragile.** This is the worst-loaded, most-expensive-sounding part of the build ("proof"), and it does not do the work its name promises.

**2. You are building gates that catch *structure* in a world dominated by *substance* failures.** The first empirical study of exactly your failure class, "Understanding Agent-Reactive Bugs" (arXiv:2607.15684, read in full), finds 255 AR bugs; the largest symptom class is **silent errors** (108/255 ≈ 42%), and specifically **statement fabrication** makes 90% of its cases silent errors. The canonical case (Codex #6562): the agent "claimed it performed a sequence of verification steps… the user never granted it access… and the harness had no record… the LLM's response is fluent… so neither the harness nor the user receives any signal that the work never happened." agpack's conformance PASS/FAIL exit codes and audit records catch **contract-shape** violations (the negative `a2a-card-bad.json` fixture correctly FAILs) — but they are silent-error blind. An agent that *fabricates completion* of a metered call, and writes an honest-looking audit record, will PASS every gate. **A harness whose "verifiability" surface only checks the shape of the run, while fabrication produces a structurally identical-but-honest record, verifies the envelope, not the content.**

**3. The repair-target argument will eat its own builder.** The same AR-bugs study shows a persistent **user-vs-developer attribution mismatch**: users 66% of the time target the harness, but developers 46% either go ambiguous or attribute to the model — worst on **Instruction Non-Compliance (15%) and Statement Fabrication (10%)**, exactly where "the harness did nothing wrong, the model misbehaved." The more the product is *the whole harness*, the more that defense ("that's an LLM limitation, not a harness bug") becomes available to itself, and the AR-bugs paper is explicit the fix location is "contested" for precisely fabrication/non-compliance. You're building a system whose correctness is defined by a stochastic oracle whose failure modes it cannot distinguish from its own — and the field's first empirical study predicts that dispute.

**4. The base rate is against "build the whole thing."** Atlan's "13 Anti-Patterns" and the production-data line (perrone, theaiengineer) report ~88% of AI-agent projects failing to reach production (Gartner-cited) — not because the LLM kernel fails, but because the **OS around it** (context management, connector reliability, permission boundaries, observability, silent-error detection) is under-invested. agpack is building the OS. The honest read: the value is concentrated in the 1–2 layers above (contract/drift, and catching silent errors), and Steps 1–5 as a monolith reproduces the 88% failure mode by scope, not by avoiding it.

Hedged where the evidence is thin: AgentAssert's Θ score and ABC's "first benchmark" are product/self claims, not replicated benchmarks, so "it exists, use it" is stronger on the *idea* than on any of these specific libraries; and I did not open the agpack source, so the "expensive" and "self-discredited" attributions rest on your 2026-08-30 caveat, which I take at face value.

## 4. THE ADJACENT FIELD (one field outside that met this shape)

**Browser automation.** The "remove the framework, give the LLM maximum freedom" move — the direct analogy to an agent-free harness — was publicly *retreated from*, and the post-mortem signal is on the comment side of a HackerHN thread on Browser-Use (news.ycombinator.com/item?id=47890841, read). The builder removed deterministic CDP heuristics for LLM freedom; an AgDex commenter: "The **'agent wrote its own helper' moment is magical in demos, but in prod you want a diff you can review**… you want a minimal harness with good logging, so you can replay the CDP calls post-mortem." What transfers, concretely: **in production, verifiability is a "reviewable diff" property, not a "deterministic proof" property.** agpack chases the latter (the portability proof — prove byte-identical output across engines); the browser-authentication lesson is that the thing that actually earns trust downstream is "give me a run I can diff and replay," i.e. trace + logging + audit that captures *what happened*, not a proof that a re-exec would match. You may be proving the wrong thing.

## REQUIRED CLOSE

### ONE THING TO CONSIDER ABANDONING
**The portability proof as a verifiability linchpin — the `proof.py` + `DeterministicFingerprintDriver` pair (and the framing of Step 4 as a "cross-engine proof").** It has the worst effort-to-payoff of the build: it is (a) the most auditable-sounding artifact, (b) *self-admittedly* not a cross-engine test (same pure-Python exec path, only a DFD# envelope), (c) the part most exposed to the §3-1 hardware-fragility problem (cross-engine determinism is empirically broken across GPUs), and (d) the least load-bearing if "verifiable" is going to mean silent-error-fraud-resistance (§3-2), which it can't certify today anyway. **Replace it** with two smaller, honest artifacts: (i) a **real second-execution-path cross-check** — run one or two bundle files through a genuinely different interpreter (Python `ast`-reformatted exec, or a WASM/container driver if one can be installed) and assert equivalence; if you can't, stop calling it a proof and call it a "contract self-consistency" test — (ii) redirect the same effort into **a silent-error / fabrication gate** (see §3-2): an audit check that the audit record's *claimed* tool-call set is reconciled against the *actual* tool-call log and against tool-call evidence on disk — the one place agpack's gates are currently silent. Reuse your own MeteredBroker audit records rather than building a new proof engine.

### ONE CHEAP EXPERIMENT (falsifiable, < 1 hour)
**Prove the portability proof isn't verifying what it claims, in one shot.** Take 6 real bundles/runs that pass your portability proof today. For each, run (i) it twice in the current env and record the computed value; (ii) re-run after perturbing one environmental input that a *different engine* would also perturb — set `PYTHONHASHSEED` to a different value, and if two Pythons or a WASM driver is available, use that; record whether the "same bytes → same result" envelope still matches. Separately, take 2 runs where the agent **fabricates** a tool-call/completion that never happened (the SF pattern from arXiv:2607.15684, Codex #6562) and feed them through the MeteredBroker + audit record. **Falsify the current approach if either:** the envelope breaks under the perturbation (proving determinism is environment-specific, not bundle-specific — the proof certifies nothing real), *or* a fabricated run produces an audit record that passes the current gate as honest (proving the verifiability surface is structure-only). Either outcome shows the linchpin is not what the "verifiable-agent" name promises, and you can stop shipping it as one.
