# GCP installation preflight and control artifacts

The management CLI now has a resumable installation journal for the artifacts used
by the independent cleanup runner. This is separate from the workload lifecycle:
**upload readiness is not permission to create GKE or Cloud SQL.** The production
workload-create authorizer remains closed.

## Prepare locally

Start with a fresh compiled [infrastructure bundle](OWS-GCP-INFRASTRUCTURE.md), its
unstarted lifecycle state, and a cleanup image digest in the separate control
repository. Do not reuse an expired trial plan by editing its timestamps.

```sh
ows deploy gcp installation prepare --state ./gcp-lifecycle \
  --guard-image 'REGION-docker.pkg.dev/PROJECT/ow-PREFIX-control-images/ows@sha256:DIGEST' \
  --out ./gcp-installation
ows deploy gcp installation status --state ./gcp-installation
```

`prepare` and `status` are offline. State is private, locked and bound to the exact
compiled plan, original lifecycle request ID and immutable cleanup image. A
pre-upload scope marker is never published as an actual source generation.
The initial source ZIP and its digest are generated by the CLI, not taken from
an arbitrary local archive or an untrusted Terraform module.

## Observe readiness

```sh
ows deploy gcp installation preflight --state ./gcp-installation \
  --out ./gcp-installation-preflight
```

This uses an ephemeral token for the exact setup identity through the existing
operator's `gcloud` login. It never enables APIs, changes IAM, runs Terraform or
creates cloud resources. It checks:

- Exact active project ID and number; required enabled APIs.
- Existing control bucket project/privacy/versioning and effective setup
  permissions to read metadata, read objects and create objects.
- The exact cleanup image digest and bounded image size in the control registry.
- The selected **zone's** GKE master/node versions and Ubuntu containerd image.
- Regional total/E2 CPU and balanced-disk headroom for **three** simultaneous nodes
  during the transient-default-pool phase, rather than only the final two nodes.

Checks explicitly distinguish required artifact-upload prerequisites from partial
workload observations. Full SQL/NAT/address quotas, regional capacity reservation,
OpenShell kernel/NetworkPolicy compatibility, private management-plane access,
executor/node/cleanup authority and fresh conservative prices/prior spend remain
separate gates. The report never substitutes declared spend for measured billing.
`artifactUploadReady` may be true while `applyReady` remains false.

## Install and reconcile artifacts

The foundation bucket/registry and image must already exist under reviewed
permissions. Upload dispatch also performs a fresh preflight; an old report cannot
authorize a later write. Accept the exact digest printed by `prepare`:

```sh
ows deploy gcp installation upload --state ./gcp-installation \
  --allow-experimental-cloud --accept INSTALLATION_DIGEST
```

Only three bounded objects are installed, in order: the deterministic binary
source ZIP, the generation-bound immutable control, and the initial checkpoint.
Each intent is fsynced before upload. GCS `ifGenerationMatch=0` refuses replacement;
the ZIP uses `application/zip`. Acknowledgements are followed by generation-pinned
read-back and byte verification before recording a receipt. Plan expiry is checked
again at each prospective upload, not just at command startup.

For an interrupted command, reconcile observed outcomes without a cloud mutation:

```sh
ows deploy gcp installation reconcile --state ./gcp-installation
```

A matching existing artifact can produce the missing local receipt. An object
absent after a dispatched intent remains **unknown** and never causes an automatic
upload replay. Conflicting bytes, replacement generations, another control's
checkpoint or changed local payloads cause a refusal. An advanced checkpoint is
validated and preserved, never reset. The original random checkpoint payload is
retained locally; a lost payload is not silently regenerated after dispatch.

## Export the actual cleanup installation

```sh
ows deploy gcp installation package --state ./gcp-installation \
  --out ./gcp-cleanup-install
```

This produces the existing pinned Terraform job/Scheduler package using the
**actual source receipt**, the exact installed control and the retained initial
checkpoint. It no longer requires the operator to transcribe a generation or
create a second, inconsistent checkpoint. Control Terraform explicitly
impersonates the bound setup account; it does not silently deploy using a broader
ambient ADC identity. Provider credentials remain outside the graph/state inputs.

Foundation and job/Scheduler resource creation are still a **separate reviewed
Terraform installation step**. The CLI does not yet automate that apply or grant
its prerequisite permissions. `permissions-request.json` remains an authority
request, not an applied/effective IAM policy. No image is pushed automatically.
After installing the reviewed package, check the original job configuration,
scheduler and independent heartbeat:

```sh
ows deploy gcp installation verify --state ./gcp-installation
```

Verification reads source/control/checkpoint, exact job UID/image/arguments,
Scheduler target/OAuth configuration, and the matching recent heartbeat. A job
that merely exists is insufficient. This command does not invoke the job, extend
the trial, create a cluster or certify all-account cleanup.

See [the implementation ledger](OWS-GCP-INSTALLATION-PLAN.md) and
[the GCP trial ledger](OWS-GCP-TRIAL-PLAN.md). Native protocol/loopback HTTP tests
cover real binary upload MIME, generation preconditions, lost responses, drift,

review, the separate control installation, scoped effective permissions and live
